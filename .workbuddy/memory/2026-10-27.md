## 等高线 SRTM「自动下载 DEM」链路接通（#88 遗留 WIP）

`44899a8` 等高线渲染落地但" SRTM 下载链路待接"。本日补齐：

- 新增 `tools/download_srtm.py`（**仅 Python 标准库 urllib+gzip，零第三方依赖**）：
  给定 `--bbox` 算出覆盖的 1° 瓦片 `N37E114`，从 `--mirror` 下载
  `<mirror>/N37/N37E114.hgt.gz` 并就地 gunzip 为 `.hgt`。默认镜像 AWS skadi
  （`https://s3.amazonaws.com/elevation-tiles-prod/skadi`，自动回退 alt 主机）；
  单瓦片失败不致命（海洋/无数据/被墙都降级），支持 `--keep-gz` / `--mirror`。
- `tools/gen_contours.c` 增加 `--download[=MIRROR]` 与 `--downloader=PATH`：
  加载瓦片前调 `python3 download_srtm.py` 预取缺失瓦片；脚本找不到/下载失败
  **降级为现有"跳过缺失瓦片"行为，不致命**。不带 `--download` 时行为完全不变
  （仍是零链接期外部依赖）。脚本路径探测顺序：`--downloader` > `$GEN_CONTOURS_PY`
  > `argv0/../tools/` > `tools/`（cwd）> `$NAVIMAP_ROOT/tools/`。
- 离线 `file://` 伪镜像端到端验证通过：瓦片命名/URL 构造/gunzip 全对；
  `gen_contours --download` 实跑拉到 1 张瓦片并产出 contours/polyrefs/pts 三件套（rc=0）。

### 用法
```
python3 tools/download_srtm.py --bbox=39.4,115.4,41.1,117.5 --out=/tmp/srtm \
    [--mirror=URL]
# 或一步到位（生成等高线 + 自动拉 DEM）：
gen_contours --out-dir=products/graph/beijing --hgt-dir=/tmp/srtm \
    --bbox=39.4,115.4,41.1,117.5 --download
```

### 跨平台注意事项
- Windows 副机（MSYS2）跑 `gen_contours --download` 需 `python3` 在 **Windows PATH**
  （不是仅 MSYS2 PATH）；否则 system() 调 cmd.exe 找不到 python3 → 自动降级跳过下载。
- 中国大陆直连 AWS S3 不稳，可用 `--mirror` 指向可达镜像/代理。
- regress 门禁仍 76/3（gen_contours 不在受测用例里；本改动为纯增量，未引入回归）。

## PBF 下载"先查本地、有更新才询问"（`download_dialog.cpp`）

用户审计结论：SRTM（download_srtm.py）已有"先查本地、缺失才下载"，但 PBF 下载
（`DownloadDialog::startDownload`）原本无条件下载覆盖。用户定调"存在即跳过下载"，
后追加"存在时比对远端新鲜度、有更新才弹窗询问"。改动：

- `startDownload()`：本地 pbf 已存在且非空 → 发 `m_nam->head()` 比对远端；
  不存在则直接 `beginDownload()`。
- 抽出 `beginDownload()`：承载原先真正发起下载的逻辑（get + 进度/落盘连接），
  被"不存在"和"用户确认更新"两条路径共用。
- 新增 `onHeadFinished()`：HEAD 回包比对 `Last-Modified` / `Content-Length` 判远端是否更新；
  - 比对失败（无网络/不可达）→ 稳妥跳过（不覆盖本地）；
  - 无更新 → 跳过；
  - 有更新 → `QMessageBox::question` 询问"是否下载更新"，选否则保留本地。
- 重定向策略用 `#if QT_VERSION >= 5.15.0` 守卫（本机 Qt5.11.3 无该枚举，副机 Qt6 默认跟随）。
- `QDateTime::fromString(..., Qt::RFC2822Date)` 解析 Last-Modified；`onMapsDownloaded` 不触发
  （跳过下载时不弹"下载完成"，避免误导）。
- 增量编译 navmap_qt 零警告（BUILD_EXIT=0）。

## 调研：本项目能否用瓦片缓存（2026-10-27）

用户提问。结论：**技术上可行且实现成本比预期低，但只在"纯平移"有效；标注必须排除在缓存外**。

**现状（实测）**
- `map_canvas.cpp:53 renderNow()` → `app_render_to_buf()` **整缓冲全量重画**；`need_redraw` 是布尔量、
  不是脏区域。拖拽时每次 `mouseMove` 都设 `need_redraw=1` ⇒ **每个鼠标移动事件一帧全量重画**。
- 帧时间（8 省北京）：z9 113 / z11 51 / z13 35 / z15 16 ms。

**★ 否决一条便宜替代方案（这条最有价值）**：原以为"拖拽时降 LOD"能顶替，**实测不成立**。
z9 各 `max_class` 档：0→94ms、1..4→111~115ms（edges 从 229,617 降到 588,302）。
z11/z13 同样：**面恒 31 / 21 ms，与 max_class 无关**（z13: 面21路7 → LOD=0 时 面21路1）。
⇒ **max_class 只控制"路"，管不到"面"**，而面是最大的单项成本。
⇒ 降质最多省 18~25%（z9 115→94），**不够**。

**架构已就绪（关键利好）**
- 数据层按瓦片索引组织（`tileidx`），`paint.c:283/374` 绘制循环本来就是
  `for ty { for tx { tile_dir(...) } }` ⇒ **"只渲染指定瓦片区域"只需收窄迭代范围，
  不用改数据格式**。这与"面 tile 索引被否"不冲突：那次否的是"给面**加**索引"（收益上限 3ms，
  因为遍历 58.5 万面记录只值 3ms），不是"按瓦片渲染"。

**量化（拷贝是实测，收益是按几何推算）**
- 整屏 4MB memcpy 实测 **0.36 ms**；单块 256px 瓦片 256KB **0.010 ms**（20 块 0.20ms）。
- 1280×800 / 256px = 5×4=20 块，含边界余量 6×5=30 块 → 缓存内存 **5~7.7 MB**。
- 平移 dx<256px（绝大多数拖拽）⇒ 新露 1 列 ≈ 5/20 块 ⇒ 重画 25%
  ⇒ 预期 z9 **113→~29ms**、z13 **35→~9ms**。★ 这是推算，未实现验证。

**三条硬约束（必须说清）**
1. **缩放全部失效**：每次 zoom 变化，所有瓦片作废（nav-desktop 的"冷帧 200~570ms"就是这个）。
2. **旋转全部失效**：`view.rot` 变化后轴对齐瓦片无法复用（Ctrl+拖拽）。
3. ★★ **标注不能进缓存**：`labels.c:233 g_grid` 是**全屏唯一的静态避让网格**
   （屏幕坐标 `/ g_grid_w` 定格位）。按瓦片独立渲染会让边界处的标注**重复画**。
   ⇒ 正确切法是**底图（面+路+线）进瓦片、标注每帧全量重画**——标注只占 2ms，完全可接受。
   这个切法正好绕开最难的坑。

**建议**：z13+ 本来 35ms=28fps 够用，收益边际；**真正受益的是 z9/z11 的概览拖拽**
（113/51ms = 9/20fps）。若要做，先只对 `zoom<=11` 开瓦片缓存、且仅在"纯平移"时启用
（zoom/rot 变化即整批作废），能拿到大部分收益而避开缩放/旋转两大失效场景。

## 底图瓦片缓存：试做后**放弃**（2026-10-27，代码已全部回退）

用户确认"会在 z9–z11 拖动地图找地方"⇒ 值得做优化。我实现了完整一套并实测，
**三种条带方案全部失败**，收益始终没出来，已 `git checkout` 全部回退（回归确认 0 差异）。

### 已做且已验证有效的部分（也在回退里，但结论留着）
- `paint_frame` 拆成 `paint_frame_stage(rs,a,st,want_base,want_overlay,pv,clip)` 是**纯重构**：
  用 `git stash` 拿改动前二进制做 A/B，三张图（含 8 省 z9）**全部 0 差异**。
  拆分点：底图段 = 背景/面/路/线/等高线；覆盖段 = 标注/轨迹/路线/车头/面板。
- `mapset_set_view` 必须**始终用全视口 bbox**，否则条带的小 bbox 会让"进省才加载、
  离省卸载"误判成离省 ⇒ 省被卸载又重建，来回抖动。

### 三个实测结论（这是本次最有价值的产出）
1. ★ **"把条带当独立小视口渲染"不可行**：绘制里大量可见性判据依赖**视口尺寸**
   （"两端都在视口外就跳过""整个面在视野外就不画"）。小视口下横跨全屏的长路/大面
   被误判成"完全在外"而跳过。实测北京 z12 右移 137px：差异 **64634 像素、
   全部集中在最右侧补绘竖条**（左侧复用区 0 差异）。省了投影但漏画要素。
2. ★★ **"只设 raster clip"（视口仍全屏）是负优化**：tile 迭代与顶点投影仍按整屏做，
   而"竖条+横条"= **两次全屏遍历**。实测 z9 平移帧 **226ms vs 无缓存 114ms**、
   z11 89 vs 51、z13 63 vs 35 —— **比不加缓存还慢一倍**。
3. ★★ **"全屏视口 + 收窄 tile 迭代范围"（理论上正解）也没跑通**：在 `tile_range()`
   一处加 `paint_set_tile_limit()` 求交（三个 paint_* 唯一的范围计算点），
   收益仍不明显（z9 159ms），且污染了全局状态导致复用区差异涨到 10%。
   ⇒ 全局状态这条路要么改成传参（侵入 3 个函数签名 + 全部调用点），要么放弃。

### 两个不可消除的固有障碍（与实现方式无关）
- ★★ **亚像素**：`mv_project` 对每个要素做 `lround`。视口中心一变，同一要素重新舍入
  ⇒ 边缘差 1 像素，复用区天然有 **0.14~0.2%** 像素不同。这不是缓存的 bug，
  **不用缓存重新渲染也会重采样**，但意味着"逐像素完全等价"做不到。
- ★★★ **整数像素平移无法精确表达**：`nm_mercator_y_fast` 是**查表插值**、与
  `nm_mercator_inv` **不互逆**。想"把中心精确挪 dx/scale"做不到；来回平移还会
  **累积**误差（实测回位置1再回位置2，差异从 0.2% 暴增到 74%，位置真的跑偏了）。
  ⇒ 在"以 lat/lon 为中心的视口模型"下，这是硬限制。要破只能在 MapView 里加
  "像素偏移"字段（改投影/反投影/drag 语义），侵入太深。

### 另一条被否的便宜路线
- **拖拽时降 LOD（max_class）**：实测只降 18~25%（z9 115→94），因为
  **max_class 只控制"路"，管不到"面"**（z11 面恒 31ms、z13 面恒 21ms，与 LOD 无关），
  而面是最大单项成本。不够。
- **同视野降分辨率**（z(n)@1280 vs z(n-1)@640）：114→70ms，只有 1.6x。因为
  投影成本不随像素数下降。

### 最终结论
**在现有架构下，瓦片缓存/条带补绘不值得做。** 三条路各有硬伤，且最重要的是：
**优化目标选错了** —— 真正该压的是"面"的绘制成本（z9 面 59ms 里投影 32ms），
而"面 tile 索引"已被历史实测否决（遍历 58.5 万面记录只值 3ms）。
若要继续，方向应是：把 `paint_areas` 的顶点投影改成**批量/增量**（项目里已有
`mv_proj` 批量版的先例，比逐点快 45%），而不是在外围加缓存层。

**环境限制（非代码 bug）**：本沙箱到 AWS S3（`elevation-tiles-prod/skadi`）的**数据体带宽被掐到 ~15KB/s**（curl 实测 HTTP=200 但 200s 仅 3.5MB、500s 仅 7.8MB 仍截断）。`download_srtm.py` 每瓦片 90s 超时 → 完整瓦片在此网络下不可行（一个 SRTM1 瓦片约需 28 分钟）。下载机制本身正确（python 起、S3 通、数据在传），只是带宽不够；正常网络下 `tools/download_srtm.py` 早前已成功拉过 4 块北京瓦片。
