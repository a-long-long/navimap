（像素级）这条路本项目 10-27 已试做并全量回退；真正值得做的是把"分 tile 数据加载"从主线程
挪到后台线程——收益小但确定。**

### 结论与建议（按性价比排序）

1. **像素级"瓦片缓存"（缓存渲染结果再 blit）= 已否决，别再试**。2026-10-27 试做过并全量回退：
   条带当独立小视口漏画大要素（64634 px 差）；只设 raster clip 是**负优化**（z9 226 vs 114 ms）；
   全屏视口+收窄 tile_range 无收益（z9 159 ms）且污染全局状态。硬障碍：亚像素 `mv_project` 用
   `lround`（复用区天然 0.14~0.2% 差 1 px）；`nm_mercator_y_fast` 查表插值与 `nm_mercator_inv`
   **不互逆** ⇒ 整数像素平移无法精确表达、来回平移累积误差（0.2%→74%）。
2. **可行且推荐：把 `src_load_disp_tiles` 的"加载+拼接"搬到后台线程**（架构完全就绪）：
   - 底座已有三处后台线程先例：`dmap_worker`（PBF 显示层异步解码，**主线程零阻塞**，
     `mapset_publish_display` 每帧收割）、`nav_worker`（算路）、`tts_worker`（语音）；
     平台层 `plat.c` 已有 `nm_thread_spawn`/`nm_mutex_*`/`nm_cond_*`。
   - 做法照抄 `dmap_worker` 的 job 槽模式：`mapset_set_view` 里检测 tile 集合签名变化 ⇒ 派发
     后台任务 ⇒ 主线程下一帧 `publish` 已完成的拼接缓冲 ⇒ 期间用上一帧缓冲继续画（渐进式）。
   - 收益：**首帧 16.5 ms 不再卡主线程**（唯一真实卡顿点）；平移帧 0.05 ms 本来就不卡 ⇒
     **总收益 ≈ 16.5 ms/换省，收益有限但确定、零风险**。
   - ★ 前置条件：**必须先重抽 provinces 让 `disp.idx` 存在**，否则这条路径根本不执行（见上）。
3. **更值钱的方向（10-27 已指出、仍未做）**：压"面"的绘制成本（z9 面 55 ms，其中投影占大头）——
   `paint_areas` 逐要素投影应改批量/增量（项目已有 `mv_proj` 批量版先例，比逐点快 45%）。
   这才是帧率的真瓶颈；缓存层在外围帮不上。

## 「批量投影优化」：实测归因后**否决**（2026-10-29 下午）

用户拍板"先做批量投影优化"。按 `rendering-perf-bisect` 技能做完完整归因后，
**结论是这条路的收益不足以做** ⇒ 没改任何生产代码，只把结论刻进
`src/render/paint.c` 的 `project_ring` 上方（留档，防下一个人再想一遍）。

### 实测方法（三条独立证据互相印证，非反推）

1. **标定法**（§13「额外多做 N 次」）：探针让每帧多投影 N 次（画面不变）。
   z9：EXTRA=1 → +7ms（1,254,452 次）、EXTRA=8 → +65ms（10,035,616 次）
   ⇒ **单次投影 5.6 ns**，一帧真实投影 125 万次 ⇒ 投影整项 = **7 ms**。
2. **替代法**：把投影换成"仍在视口内的线性近似"（x 精确 + y 用视口中心处
   dy/dlat 线性系数）⇒ z9 省 **7 ms**、z11 2 ms、z13 1 ms（与 ① 吻合）。
   ⚠⚠ **第一版替代版漏了"锚在视口中心"** → 整幅图被平移到视口外，
   `edges_drawn` 从 588302 掉到 **218**（99.96% 的路被视口裁掉），
   测出来的"更快 −52ms"**全是假的**（这是 skill §9-1 的坑，实际踩到了）。
   修正后要素数与正常版**完全一致**（588302/113933/33764）才敢采信。
3. **位开关判别实验**（NAVIMAP_PAINT_DIAG 位）：面不填 −11ms / 面不描 −8ms /
   路不画 −2ms / 线不画 −2ms；**全部不落笔仍要 84 ms**。

### z9 单帧 110 ms 完整归因

| 项 | 成本 | 依据 |
|---|---|---|
| 落笔（面填充 11 + 面描边 8 + 路 2 + 线 2） | **23 ms** | bits 判别实验 |
| 顶点投影（125 万次 × 5.6 ns） | **7 ms** | 标定法 + 替代法互验 |
| 顶点取数（project_ring 整项 21 − 投影 7） | **14 ms** | RING_EXTRA 标定 |
| └ 其中"消除随机访存"能省的部分 | **8 ms** | 影子表预演（像素 **0 差异**） |
| 剩余（遍历 67.7 万条面记录 + 预筛 + 分支） | **≈66 ms** | 差值 |

补充实测：
- 面记录扫描 **67.7 万条/帧**，视口内只有 11.4 万 ⇒ **命中率 17%**（z11/z13 更低到 6%）。
- bbox_cache 全量顺序扫 9.4 MB ≈ **1 ms/遍** ⇒ 不是瓶颈。
- `nm_mercator_y_fast` 在 LTO 下**已被完全内联**（exe 的 nm 里它无任何调用点）
  ⇒ skill §20 那 1 ms 早就拿到了。
- 活动边表（AET）填充已做（skill §10），像素 0 差异。

### 为什么不值得做（三个候选的实测上限）

| 方向 | 实测上限 | 占比 | 障碍 |
|---|---|---|---|
| **批量/向量化投影** | **7 ms** | 6% | §19：唯一能拿 ~9ms 的手段（除变乘）**改浮点结合顺序 ⇒ 整图 diff 抓到 1 px**；纯等价改法只值 1 ms（且已拿到） |
| **坐标内联进 polyrefs** | **8 ms** | 7% | 要改落盘格式 + 全量重建 8 省 + polyrefs 4B→8B；**像素 0 差异**（影子表预演） |
| 瓦片缓存（像素级） | 0 | - | 10-27 已试做并全量回退 |
| 异步加载 | 0 | - | 帧时间 100% 是 CPU，I/O 已摊平 |

⇒ 真正的大头是"剩余 66 ms"（遍历 67.7 万条面记录 + 预筛），但它**不是可替换的算子**：

### 方法要点（可复用）

- **净损失面积**这个判据比 `bmpdiff.py` 的 Top 转移更严格也更可靠：Top 转移只看前 10 名，
  会被"填充↔描边互换"掩盖住真正的单向面积损失。做法：自写脚本按背景色
  (244,241,234) 分流，统计 `to_bg` 与 `from_bg`。
- **判"丢要素"必须看方向，不能看差异率**（skill §11）：抽稀那版差异率只有 3.5%，
  但净损失为正 ⇒ 仍是丢要素。
- 看图需要 BMP→PNG（无 PIL）：纯标准库 zlib+struct 手写转换即可。
- 扫参数要**逐档重编**（`AREA_DOT_PX` 是编译期常量），且**各缩放级要用各自的基线图**
  —— 我第一次拿 z9 的基线去比 z11/z11 的图，算出"负净损失"的假象。

## 补2：北向标签带号 + 拼接 bug（b8f533f）

J 先生再追"把带号也加到北向标签"。初版用 `zone*1000 + Xk/1000`（数值相加）：
