- 新增 RevIdx：按省惰性构建的反向 CSR（边记录只有 EF_TO 没有 EF_FROM）。
  list 存 from 节点而非边下标——拿到 from 后扫它的出边找 EF_TO==nd
  （出度个位数），省 4 字节/边。
- ★ 反向 CSR 前缀和：必须 `for(i<n){c=start[i+1];start[i]=acc;acc+=c;} start[n]=acc;`。
  写成 `for(i<=n){c=start[i];start[i]=acc;acc+=c;}` 漏掉 cnt[n-1]
  ——最后一节点的入边区间被截成空（实测踩中，表现为"不连通"）。

## 修 sync_maps.sh：先删后搬 → 先让位后搬（残留问题的根因）

- 根因：`mv "$tmp.log" "$tmp/extract.log"; rm -rf "$dir"; mv "$tmp" "$dir"`。
  删除一旦被拦（目录还在），mv 就把新产物塞进旧目录变成 `$dir/$name.tmp.PID` 嵌套垃圾，
  而脚本照常打印 [ OK ] —— 1.45 GB 残留就是这么来的。
- 修法（scripts/sync_maps.sh）：
  1. 顺序改成 **旧目录先改名让位 → 新产物 mv 就位 → 再删旧**，mv 失败就把旧目录换回去；
  2. 每一步都查返回值，`mv`/`rm` 失败一律 [FAIL] + n_fail，不再假装成功；
  3. 新增 `drop_tmp()`：删完回头看路径还在不在，还在就打印提示并计入 `n_warn`
     （汇总多一栏"残留待清理 N"）；旧目录删不掉只警告不算转换失败——新产物已就位。
  4. 顺手加 `mkdir -p "$OUT_ROOT"`（演练时发现输出根不存在会让 extract 直接炸）。
- ★★ 演练方法（可复用）：**验证"删除/替换"类脚本修复，别只在正常路径下跑**。
  把脚本 sed 成副本（改 OUT_ROOT/SRC_DIR 到 /tmp，并把 `rm -rf ` 替换成 `false #`），
  就能稳定复现"删除被拦截"，然后新旧逻辑各跑一遍做 A/B：
  - 旧：`tianjin/tianjin.tmp.51011` 嵌套垃圾，产物 93M→**186M**，仍打印 [ OK ]（静默）；
  - 新：产物干净 93M/12 文件，旧目录留在同级 `.old.PID`，明确警告 + "残留待清理 1"。
  ⇒ 完全复现了真实故障形态，修复必要性无须靠推理。
- ★★ 坑：`command -v rm` 返回裸 `rm` 说明它是 **shell 函数**，优先级高于 PATH
  ⇒ 想模拟 rm 失败，**放 PATH shim 没用**（函数先命中），`export -f` 也被环境注入的
  safe-delete 覆盖。可靠办法是靠权限（chmod 500 造一个真删不掉的目录）或直接改脚本副本。
- 演练用 tianjin（16MB pbf，2 秒）做最小省，别拿 shaanxi（10 秒+）练。
- 演练副本 scripts/_drill_*.sh 与 /tmp 演练目录已用 /bin/rm 清干净，8 省 ASSERT-OK。

## 结论：graph_v2 可删，但程序不会自己重建（实测）

## ★ 修 navsim 1.1m 断言失败：seg_m 踩了和 seg_ds 一模一样的坑

- 现象：`--from=39.90,116.40 --to=39.95,116.45` 报
  "已走+剩余 != 全程，最大偏差 1.1 m" + "到达后剩余里程 1.1 m 不为 0"；
  长路线（跨城 90 km）却 NAVSIM-OK —— **偏差恒为 1.07 m，与路线长度无关**，
  这是识破它的关键线索（不是浮点累积，是两套口径的差）。
- 根因（src/route/route.c）：
      out->seg_m[i] = (uint32_t)(meters + 0.5);   // 段长存整数米
      tm += meters;                                // 全程却累加**精确** meters
  而紧挨着的 seg_ds 早就修过同一个坑（注释写着"total_s 用舍入后段耗时累计，
  各自四舍五入再求和几千段能差 ~2 s"）—— **seg_m 这边漏改了**。
  ⇒ Σseg_m(整数) ≠ total_m(精确)，差 1.07 m。
  导航的"剩余里程"是按 seg_m 累加的投影里程，于是 已走(精确)+剩余(整数基准) 对不上。
- 修：`tm += out->seg_m[i];`（照抄 seg_ds 的做法，自洽优先于绝对精度）。
- 验：短/长路线恒等式误差均 **0.000 m**，到达剩余 0.00 m，两条 NAVSIM-OK；
  route_cli 跨省 3909 段 ROUTE-OK、渲染 route_pixels 断言 ASSERT-OK、8 省 ASSERT-OK。
- ★★ 教训：同一个"精确值 vs 舍入值"的坑，在同一个函数里修了 seg_ds 却漏了 seg_m。
  改这类成对字段时要问一句"另一个呢？"；判据要写成恒等式断言（正是它把 bug 抓出来的）。
- ★ 调试踩坑：临时 printf 用 `%f` 打印 `uint32_t seg_m[]` 会读出假值（我一度被
  误导以为 seg_m 是前缀和）。打印前先看字段类型。

## ★ 双向 A* 终止条件：默认那个不保证最优（做成 --exact 开关）

- 起因：城内短途 bidir=1 与 bidir=0 结果不一致（同起终点、吸附完全相同）
  bidir=1 → 152 段/10.13 km，bidir=0 → 160 段/10.39 km；而长途两者一致。
- 排除过程（每一步都用对照实验排除一个假设）：
  1. 先怀疑 h 高估（H_SPEED_KMH=130 < 某些边限速）→ 换 `--mode=dist`
     （h=直线距离，严格可采纳）**仍不一致**，且单向 9.53 < 双向 9.57，
     方向与"h 高估"相反 ⇒ 排除启发式。
  2. 再怀疑两段限制过于保守 → `--no-restr2` 后仍差（9.55 vs 9.53）⇒ 排除限制。
  3. 最后锁定终止条件 `ff + fb >= best`。
- 根因：终止条件 `两侧堆顶 f 之和 >= best` **不充分**。它允许一侧堆顶远小于
  best，最优接缝可能还埋在那一侧没展开 ⇒ 提前收工，返回次优解。
- 正确条件应为 **max(ff,fb) >= best**：若存在更优解 C* < best，它必经接缝 n，
  两侧 f_F(n) <= C*、f_B(n) <= C*（h 可采纳）⇒ 两侧堆顶都 < best ⇒
  max < best ⇒ 不会停。改后双向与单向结果**完全一致**（dist 均 9.53、time 均 10.39）。
- 代价（京→郑实测）：max 条件要两侧都搜到 best，
  233 万节点/7.2 s → **787 万节点/54.8 s**，比单向（467 万/18.8 s）还慢。
  ⇒ 这是本质 trade-off，不是实现问题（best_cut 剪枝 `f < best_cut` 已在生效）。
- 处理：`RouteOpts` 加 `exact` 字段，route_cli 加 `--exact`。
  默认 `ff+fb`（快，实测次优幅度 dist 模式 +0.4%），验收/对拍用 `--exact`。
  注释里把两组实测数字都写进去了，免得后人再猜。
- 判据：`--exact` 与 `--bidir=0` 的结果必须一致（这才是有意义的 A/B 对照）。
- 回归全绿：navsim 短/长 OK、restr_ab RESTR-AB-OK（开限制后 0 条踩禁行）、
  渲染 route_pixels 断言、8 省 ASSERT-OK。

## 帧时间第六刀：描边 / 线批量化（同日下午）

  找后继），这次用在**面/线既有顶点序列**上净赚 —— 差别在附加机器开销，手段本身无对错。

## 帧时间第七刀：查"多省放大"，结论是**必须改数据格式**（傍晚）

- ★ 判别实验 1（1/2/4/8 省逐级加载）：**不存在多省放大效应**——单河北一省就要
  379ms/558839 边，与 8 省几乎相同；之前"8省 vs 单省"其实比的是"河北 vs 北京"。
  ⚠️ 坑：构造临时图集不能用 symlink（mapset 会解析成真实路径 → 8 省全加载），
  必须用**硬链接**且在同一文件系统内（跨设备 ln 会失败）。
- 判别实验 2（河北单省 z9，路 469ms）：落笔 85 / **随机读 nodes.bin 195** /
  投影 39 / 其余≈150（edgelist 扫描 + 读 edges.bin + 去重 + 裁剪）。
- tile 过滤计数（北京 z9 同一帧）：扫描 2880726 → 等级不够丢掉 2512718（**87%**）
  → 反向 94238 → 视口裁剪 **0** → 画出 273770。
  ⇒ 87% 的条目只为查等级而随机读一次 edges.bin 就被扔掉；画出来的每条边还要
  随机读两次 nodes.bin。
- ★★ 三种不改数据格式的办法全部实测无效，代码已撤掉：
  软件预取（深度 48/24）455→452 无效；缓存"上一条目起点"命中 388/27万≈0 无效
  （edgelist 不按节点分组）；16K 槽节点坐标缓存 460→**487 更慢**。
- 结论与下一步（已写入 PLAN.md §21，属数据格式改动，需重跑 sync_maps，故先问再做）：
  edgelist 条目从 {node_idx, edge_idx} 扩成自带 {from/to 经纬度, cls, flags}，
  让渲染只读顺序数据；跨省去重改用"两端量化坐标有序对"当身份键，不再读 OSM id。
  粗估河北 z9 路 469 → ~140ms。代价 edgelist 约 ×2.5 + 重跑 8 省提取 + 版本兼容。
- 现状（撤销实验后、与第六刀产物逐像素 0 差异）：8 省 z9 562 / z11 198 / z13 145 ms，
  单省 z9 142 ms；回归 21/21 绿。

## 帧时间第八刀：edgelist v2（批准落地，写完 + 验收完）

- 条目 8B → 28B：`{from_lat,from_lon,to_lat,to_lon,flags u16,cls u8,pad,
  edge_idx,node_idx}`。★ 留 node_idx 是因为 edgelist 不只渲染用：route.c
  sew_cb 要 from 节点下标展开、mapset.c 重复省检测要拿条目采样——正确性路径
  不能为省 4 字节退化成"再随机读一次 nodes.bin"。
- 读取端统一出口 `xl_from_key()` / `xl_entry()`（mapset.c），渲染/缝合/去重/覆盖
  三条路径都不关心版本；渲染按 `rec_size` 分叉（8=v1，28=v2），v2 不读 nodes.bin。
- `NMBIN_VERSION` 2→3 强制全量重抽（重跑 2 分钟）。理由：混合 v1/v2 图集画面
  完全一样但体积/帧时间不同，排查时绝不会想到是版本混装。
- ★ 踩到并规避的坑：v1 用 OSM id 当去重键、v2 用坐标键 → 混合图集里两套键
  互不相认，跨省重复路会画两遍。所以 **v1 路径的去重键也改成坐标**，
  三条绘制路径现在统一用 coord_key_e7 有序对（仍不能排序成 min/max）。
- 实测（第二帧 1280×800）：单省 z9 142→119 / z11 122→109 / z13 100→97；
  河北 z9 295→251、z11 137→112；8 省 z9 551→464 / z11 196→166 / z13 145→131。
  路网分项普遍 −19%~−32%。帧 −10%~−18%。
- 验收：8 个视口逐像素 **0 差异**；regress 21/21；零警告。
- 代价：edgelist 328MB → 1.14GB，products/graph 3.0G → 3.8G。
- ★ 残留：sync_maps 换下来的 `products/graph/*.old.100818` 共约 3 GB 因
  safe-delete 拦着没删掉，需要 `/bin/rm -rf` 手工清。
- 新分解（8 省 z9 路 284ms）：去重 95 / 落笔 70 / 投影 64 / 其余 58
  ⇒ 多省场景去重已是第一大头；单省压根不启用去重（≥2 省盖住视口才开）。
- 新增 `scripts/shot_bench.sh <输出目录>`：固定 8 个视口跑第二帧、存 BMP、
  打表，改前改后各跑一次就能直接比（以前是每次手工拼命令）。

## 帧时间第九刀：砍掉多省渲染的重复劳动（8 省 z9 561→250 ms）

- 刀8 后重做归因（8省 z9 路 272ms）：**去重 116 / 落笔 75 / 投影 55 / 扫描 28**。
  去重防的 48 万条重复全来自"北京、天津整块被河北包进去"。
- ★ 措施一：被整省包含的省渲染直接跳过（window.c 三处加 `dup_of>=0`）。
  安全性是实测出来的：同视口 z13/z15 两省逐像素 0 差异，z11 河北比北京多画
  （8282px 全为"背景→要素"），三个视口 + 天津结论一致。
- ★ 措施二：去重按瓦片门控——`paint_roads` 新增 `peer_tiles/n_peer`，
  只有该格 ≥2 个省才查表（等价判据，非近似）。
- ★ 措施三：面/线不去重（不透明填充，重复画同像素）：省 22ms、0 像素差异，
  `paint_areas/paint_lines` 的 dd 参数删除。
- 顺带：去重槽从 hi/lo/gen 三数组改成 16 字节单槽（64 位指纹），省 20ms。
- 结果：8 省 z9 472→**250**、z11 171→**113**、z13 131→**97**；单省不变。
  8 省 z9 路网 284→111ms，已与单省河北 110ms 持平 ⇒ 多省这条路挖到底。
- 验收：与改前 463/332/2069 px 差异，转移全是路色↔路色（分级不同），无要素丢失；
  **8 省画面 == 只加载河北（z11/z13 均 0 差异）**；regress --build 21/21 零警告。
- ⚠️ 两个不成立（别再试）：钉小去重表（微基准 32→11ns 但现场只省 18ms，
  热路径 cache 被 29MB 顺序流冲掉）；投影 /1e7→*1e-7（GCC 已优化，0 收益）。
- ⚠️ 坑：用硬链接构造临时图集时必须加 `--no-autobuild`！否则自愈会把 sources/
  里缺的省全部重抽进临时目录（本次误建 6.5G，也是第一次跑超时的原因）。

## 帧时间第十刀：落笔归因 + 面要素分解（z9 250→228）

- 采纳：路网退化成单像素的段，紧邻前一条同像素同等级就跳过（z9 67.2% 段退化、
  95.6% ≤1px，一帧跳 12.1 万条）。路 111→88，帧 250→228，8 视口 **0 差异**。
- ★ 关键踩坑：先做的"逐像素记录最后写入等级"表**不是**等价的——非退化线段
  穿过像素时不更新表，后面同等级的点被误判跳过，16px 在两条不同等级路的
  交叉处换了赢家。改成只认"紧邻前一条"才真正等价。
- ★ 硬事实（SDL 2.30 软渲染本机实测）：
  - `SDL_RenderDrawLine(x,y,x,y)` ≡ `SDL_RenderDrawPoint(x,y)`（0 像素差异）
  - 每次绘制调用固定开销 ~100ns，与像素数无关 ⇒ 换画法没用，只有"不画"才省
  - 全部跳过退化段能省 46ms 但丢 112px ⇒ 零长线确实画了一个像素
- 面要素分解（108ms）：填充 38 / 描边 29 / 取顶点+投影 35 / 循环 10。
  用"顶点循环跑两遍"分离冷热：二遍 23ms、一遍 35ms ⇒ 冷访存只值 12ms，
  **不值得为此再动数据格式**（内联坐标进 polyrefs 上限 ~12ms）。
- 九条不成立（已撤）：攒 DrawPoints 批（批长 1.2）、像素记录表去重、
  DrawPoint 代替、整段不画、lround 内联、(lon+180)/360 乘倒数、顶点预取
  （反而慢 6ms）、fill 按视口裁剪行、fill 整数扫描转换（0 收益 + 4756px）。
- 待用户定夺（实验代码已撤，见 PLAN.md §24）：面顶点按屏幕尺寸抽稀到 12 个。
  N=2 −6ms/0.17%px；N=4 −15ms/0.87%；N=8 −25ms/1.9%；N=16 −30ms/2.7%。
  差异方向全是"填充色↔描边色"互换（轮廓粗细变化），无要素丢失。
- 验收：regress --build 21/21、零警告。
