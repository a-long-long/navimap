## 实现「只留 PBF，显示层按需解码 + LRU 缓存」（用户指令）

用户诉求（承接 10-22）：硬盘别同时存 PBF 和 nmbin；运行时只加载屏幕区域，滚出再加载别的。
选定路径：**显示层（面/线要素）从 PBF 运行时解码 + 内存 LRU**，路由图仍走 nmbin。

### 关键设计决策（都是实测驱动的，不是猜的）

1. **省粒度而非瓦片粒度**：实测 PBF 的 data blob 平均覆盖全省 43% 纬度跨度
   （北京 621 个 blob，单个跨 0.99°/1.33°，**z11 视口仍命中 53%**）⇒ 按 blob 跳读
   收益低于索引成本，**不可行**。改为"整省解一次 + LRU"。
2. **不需要扫第二遍 PBF 取坐标**：`polyrefs` 存的是节点内部下标，而这个下标空间**就是**
   nmbin `nodes.bin` 的下标空间（都按 osm_id 升序、都去掉了文件里不存在的节点）
   ⇒ 拿 nodes.bin 的 osm_id 数组做**二分查表**即可。**省掉整遍 PBF 扫描（河北约 4 s）
   与两份坐标数组（河北 105 MB）**。这一条把峰值 RSS 从 1.5 G 降到 714 MB。
3. **PBF 的 dense 节点 id 严格升序**（天津/北京/河北实测 0.0000% 逆序或重复）——
   曾用哈希表对齐，改成双指针归并后：河北 12.7 s→9.6 s、1.53 G→1.14 G。
4. **下标空间必须与 graph_build 一致**，两处收集规则：
   - refs 收集**要含路网 way 的节点**（graph_build 在"路由/线/面"三分支**之前**就累加 refs），
     少收一类 ⇒ 下标错位 ⇒ 坐标全错（我第一版就踩了，表现为坐标整体移位一位）；
   - 名字池 id 空间要与落盘版一致 ⇒ **路网 way 也要 intern 名字**（虽然不建记录）。
5. `polyrefs` 的下标来自 nmbin 的 nodes.bin ⇒ **polyrefs 逐字节相同**，
   但**不能拿自己的 polyrefs 配自己的 nodes**（下标空间会错位）⇒ 必须用 nmbin 的 nodes。

### 实现

- 新增 `src/map/pbfmap.{h,c}`：PBF → 内存版 nmbin（areas/lines/polyrefs 三个缓冲）。
- `src/map/mapset.{h,c}`：`MapSrc` 加 `loaded`/`pbf_display_mode`/`dmap`；
  新增 `mapset_set_view`（视口+50% 边距加载/卸载 + LRU 淘汰）、
  `mapset_enable_pbf_display`、`mapset_ensure_display`；`src_unload` 补 `pbfmap_free`。
- `src/main.c` / `tools/map_shot.c`：`--pbf-display=<sources目录>[:LRU上限]`。
- 新增 `tools/pbfmap_check.c`：解码结果 vs 落盘文件逐字节比对（8 省全 IDENTICAL）。

### ★ 顺带发现一个既有的渲染缺陷（与本功能无关，但被它暴露）

PBF 模式与 nmbin 模式的**文字最终像素**差 12.357%。用对照实验证明**与 PBF 数据无关**：

- 用 nmbin 显示层 + **同样的堆布局扰动**（解 PBF 但不挂载）⇒ **复现同样 12.357%**；
- **ASan（-O1）构建下 0 差异** ⇒ 优化器相关的未定义行为（ASan/valgrind 查不到，
  不是 use-after-free）；
- 差异**只在标注阶段**（地名 8.8% + 路名 3.2%）；面/路/线三阶段 raster **逐字节相同**；
- 文字绘制调用（文本+坐标）**完全相同**（362 次逐字一致）⇒ 差异在字形纹理合成本身。

⇒ 结论：**既有的、依赖内存布局的文字渲染不稳定缺陷**，任何改变堆布局的改动都会暴露它，
需要单独修。已写进 PROGRESS.md「已知限制」并列为下一阶段第一优先。

## ★★ 修掉它：根因是**悬垂纹理指针 + 指针相等当判据**（不是未定义行为）

### 定位路径（可复用的方法）

1. 先把「数据链」全部钉死：areas/lines/polyrefs/nodes 四缓冲记录区**逐字节相同**，
   area_bbox **零差异**，绘制调用（文本+坐标）**362 次逐字一致**，字形元数据
   （cp/w/h/advance/tex 存在性）**逐条相同** ⇒ 排除数据层。
2. 逐阶段 dump raster（areas/roads/lines/place/labels）⇒ 差异**只在标注阶段**。
3. ★ **dump 字形纹理的像素哈希**（`TTF_RenderUTF8_Blended` 出来的 surface 直接算 FNV）
   ⇒ **nmbin 622 条 / PBF 311 条，且前 311 条逐条相同**；nmbin 的第 i 与第 i+311 条
   **cp 相同、像素哈希也相同** ⇒ nmbin 渲染了**两遍**，PBF 只渲染**一遍**。
4. ★ dump 每帧的 renderer 地址 ⇒ **nmbin 两帧地址不同**（0x55cf60 → 0x70b700），
   **PBF 两帧地址相同**（都是 0x55cf60）⇒ 判据失效。

### 根因

`app_render_to_surface` **每帧**新建/销毁一个软件渲染器，但**销毁前没作废字形纹理**。
`glyph_get` 靠 `tex_owner != r` 判断"renderer 换了没有"，而判据是**指针相等** ——
中间的 `SDL_DestroyRenderer` 把那块内存还回分配器，下一帧 `SDL_CreateSoftwareRenderer`
很可能拿回**同一地址** ⇒ 判据认为"没换" ⇒ 缓存里的 `g->tex` 是**悬垂指针**
（旧 renderer 已销毁，纹理随之没了）⇒ 下一帧 `RenderCopy` 画出错的字。

**PBF 只是恰好改变了堆布局**，让第二帧地址复用了 —— 这个 bug 一直存在，只是没被触发。

### 修复

`src/ui/window.c` 的 `app_render_to_surface`：`SDL_DestroyRenderer(r)` **之前**
无条件 `font_drop_textures(a->font); font_drop_textures(a->font_big);`
（`app_ensure_canvas` 早就这么做，**只是漏了这条销毁路径**）。

### ★ 方法论教训（重要）

1. ★★ **SDL 对象销毁/重建的成对约定，必须在每条销毁路径上落实**，不能只靠
   "换个对象自然能判出来"——**尤其当判据是指针相等时，它对"地址被复用"完全失效**。
   `font.h` 的注释里其实已经写明了这个危险（"新 renderer 可能正好分配到旧的地址"），
   但 `app_render_to_surface` 没遵守 ⇒ **注释写了约定 ≠ 所有路径都落实了**。
2. ★ **"地址被复用"这类 bug 只在特定堆布局下显形** ⇒ 改任何影响分配顺序的东西
   （多解码一个文件、多开一个 mmap、加一个缓存）都可能把它从"不出现"推到"出现"，
   **不能因此判它是"新引入的"或"环境问题"**。
3. ★ **"某阶段的 raster 相同"不等于"该阶段没问题"** —— 因为标注走 SDL_RenderCopy
   （不进 raster），要分别看"自写光栅阶段"与"SDL 调用阶段"。
4. ★ 怀疑"未初始化内存"时，**先查对象生命周期**（谁创建、谁销毁、指针是否还活着），
   别急着上 MSan/valgrind —— 这里是**悬垂**不是**未初始化**，两个工具都查不到。
5. ★ 定位"两阶段行为不同"时，**dump 计数**（不只是 dump 内容）往往比 dump 内容更快破案：
   622 vs 311 这个"差一倍"直接指向"多渲染了一遍 / 少渲染了一遍"。

### ★ 设计缺陷自踩（写门禁时）

负向模式一开始给 `check()` 加了"反转"（g_neg ? !cond : cond），想把所有断言反转成
"必须失败"——但负向断言本身就写成 `nm_file_exists(bogus)==0` 这种**条件为真**的形式，
反转后全部误判成"意外通过"（8 项假 FAIL）。**教训：负向断言要写成"失败 Outcome 为真"，
不要写"把成功断言取反"**——否则两套语义互相打架。
