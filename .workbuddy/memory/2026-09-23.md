## 参考 OsmAnd 优化算法（PLAN.md §27）

盘点对象 /home/along/osmand-app（8.6G / 37 万文件）。关键发现：本项目的**坐标键
当搜索主键本来就是从 OsmAnd 搬的**（`route.h` 注释里写了出处 `RoutePlannerContext.cpp:132`）。

### 采纳：加权 A* → 默认 w=1.2（OsmAnd `heuristicCoefficient`）

`f = g + w·h`，`RouteOpts.heur_w`，CLI `--heur-w=`，默认 `ROUTE_HEUR_W_DEFAULT 1.2`。
★ 与 `exact` 是两个独立旋钮：exact 管终止条件，w 管贪心程度。

- 京→郑 693 km：9436 ms → **2766 ms**（3.3×），**里程完全一致 693.14**。
- 15 组路线逐个比对：14 组里程一致、1 组 w=1.2 更短（郑州→青岛 713.45 < 714.87），
  **零劣化**。提速 1.8~4.7×。城内短途（<15km）无收益也无损失。
- 安全的理由：h = 大圆距离÷130km/h 是很松的下界（绕行系数 1.11~1.21、限速远低于 130），
  ×1.2 后仍远低于真实代价。
- ★ **验收/对拍工具必须显式 1.0**（`restr_ab` 两遍、`--exact`），否则 A/B 失效。
- w≥1.5 开始真劣化（京→郑 +3.2%），w=2 +8.5%。

### 否决：Douglas-Peucker 简化几何（别再试）

OsmAnd 构建期按 zoom 做 DP 简化，但**本项目的要素分布完全不同**：z9 走完整管线的面
**91% ≤ 5 px**，小面丢一个点形状就变。屏幕坐标 DP 实测：
ε=0.5 → 243 ms（**比基线 224 更慢**）/ 1.1% 差异；ε=1 → 4.97%；ε=2 → 9.9%。
转移方向全是单向"要素色 → 背景色"（丢面积）。且 DP 在投影**之后**做，省不到投影 16 ms。
⇒ 连同 §26.4 的"阈值筛"，**"简化几何"这条路在本项目不成立**，只能走精确等价的路。

### 没搬的

- **HH 层次路由**（`hhRoutePlanner.cpp` 1519 行）：需构建期生成整套层次网络索引，
  1500 行量级子系统 + 重跑 8 省。加权 A* 用 3 行拿到 1.8~4.7×，先用便宜的。
- 构建期多级 LOD：简化本身已被否，多级只省 DP 开销，而 DP 收益不成立。
- 按 zoom 过滤要素（minZoom）/ basemap：**取舍不是优化**——低缩丢小要素城市会变空，要产品定。

## 第十二刀：面要素 + 路网各试一轮，**全部否决**（PLAN.md §28，代码零改动）

起点 z9 206 / z11 100 / z13 91（面 91、路 87）。终点：回到原样，22/22。

### 面要素 91 ms 完整归因（z9，逐项判别实验量出）

大面顶点投影+循环 32 / 填充 21 / 描边 17 / 打点 6 / bbox 投影 4 / 顶点访存 6 / 遍历 3。

- ★ **遍历 58.5 万个面记录只值 3 ms** ⇒ "给面要素加 tile 索引"上限就这么点，
  不值得改数据格式。**先量上限**（§5.11）又一次挡掉了大改动。
- ★ **一次 mv_project 只有 17.6 ns**（额外多做 22.8 万次投影只 +4 ms）。
  之前按"命中数×2 次投影"反推出的 40 ms 是错的——**能直接量就别反推**。

### 三项否决（都有数据）

1. **提高 AREA_DOT_PX**（打点 80ns vs 完整管线 2.13μs，差 27 倍，很诱人）：
   K=3 帧 187 但差异 3.18%、K=8 帧 150 但差异 11.69%，**全单向"要素色→背景色"**。
   与"抽稀""DP"是同一个坑的三种写法 ⇒ **简化几何在本项目一律不成立**。
2. **去掉描边**（17 ms）：差异 13.47%，含"建筑填充→背景"28492 px
   —— 小面（2~3px）的描边就是它本体，去掉等于丢要素。
3. **顶点坐标内联进面索引**：一次随机访存只值 **6 ms**，是天花板；要改格式+重建。

### 路网：折线合并重测（第五刀结论在 v2 下仍成立）

潜力确实大：z9 589,300 条边里 **84%（495,069）能接上一条且同等级**，平均折线 6.3 段。
但实测 z9 **0 差异却慢 7 ms**、z11 慢 2 ms —— SDL 的 `RenderDrawLines` 在软渲染器里
就是循环调 `RenderDrawLine`，**每条线段的开销一分没省**；省下的只有 SetRenderDrawColor，
被攒点/判连接性吃回去了。描边的 stroke_flush 有效是因为顺带省了"每面一次"的设色。
- ★ z13 "快 13 ms"是**假收益**：漏了 width>1，粗线被画成 1px，才有 8% 差异。
  **"加速"和"画错了"经常是同一件事**，只看耗时会把 bug 当成果。

### 剩下的唯一路

换掉 SDL 软渲染、自己写 framebuffer（588K 次调用 × ~100ns ≈ 59 ms 可直接省），
但要重写 fill_polygon / stroke_ring / paint_thick_line。是产品决策，不是优化决策。

## 「绕过 SDL 自己写 framebuffer」的影响评估（只读，未改业务代码）

用两个临时工具把上限量出来了（都在 /tmp，未进仓库）：`sdlprobe.so`（LD_PRELOAD
统计/计时）、`sdlstub.so`（把画线/点/设色变空操作，测地板）、`fbbench`（微基准）。

### ★ 结论：这一层的耗时上限（= 现状 − 空操作地板）

| 缩放（8 省 1280×800，第 2 帧） | 现状 | 空操作地板 | SDL 层上限 |
|---|---|---|---|
| z9  | 206 ms | 125 ms | **81 ms（39%）** |
| z11 | 102 ms | 57 ms  | **45 ms（44%）** |
| z13 | 90 ms  | 38 ms  | **52 ms（58%）** |

分阶段看（z9）：面 91→62、路 87→42、线 24→18、标注 3→3（文字走 RenderCopy，不受影响）。

### 调用规模与单次成本（z9 一帧）

- DrawLine 折算 91.4 万次 / DrawLines 6.16 万次 / DrawPoint 7.6 万 / **SetDrawColor 77.4 万**。
- 微基准（91.4 万条，60% 退化成 1px）：`SDL_RenderDrawLine` **59.6 ms（65 ns/次）** vs
  自写 Bresenham **19.9 ms（22 ns/次）**；SetDrawColor 单独 3.9 ms（4 ns，不是 42 ns——
  探针计时版被 clock_gettime 抬高了 ~13 ns/次）。
⇒ 净收益 ≈ 81 − 20 = **60 ms，z9 206 → ~146 ms（−29%）**。**不是数量级的变化。**

### 三个实测事实（决定改造方案）

1. **可以渐进替换，不必重写**：`SDL_CreateSoftwareRenderer(surface)` 就画在
   `surface->pixels` 上，**没有双缓冲、不需要 RenderPresent 同步**——自己写像素和
   SDL 画可以混在同一张图上（已验证：自写的绿点和 SDL 的红点同存）。
2. **像素格式是 `SDL_PIXELFORMAT_RGB888`**（Rmask 00ff0000、Amask 0），不是 ARGB8888。
   自己写像素必须按 `surface->format` 的 mask 打包，否则红蓝颠倒。
3. **越界坐标 SDL 不崩，自己写会崩**（微基准第一版就段错误）。
   ⇒ 自己写必须自带裁剪，这是最容易踩的坑。

### 代价清单

- 要改 paint.c(14 处) + navdraw.c(20 处) + font.c(2) + map_shot.c(2)，约 1700 行签名
  从 `SDL_Renderer*` 换成自己的 framebuffer。
- **文字**：现在字形是 SDL_Texture + RenderCopy + ColorMod（385 次/帧）；自己写要把
  `TTF_RenderUTF8_Blended` 出来的 ARGB surface 自己 alpha 混合，阴影/彩色也要自己来。
  但标注只占 3 ms，**工作量最大、收益最小**——建议留在 SDL。
- **半透明面板**（navdraw 的 SDL_BLENDMODE_BLEND 六处）要自己实现 alpha blend。
- **窗口路径**要改上传：自写 fb → `SDL_UpdateTexture` + `RenderCopy` + Present，
  实测 **+2.6 ms/帧**（4 MB 上传+拷贝）。离屏 map_shot 不受影响。
- regress.sh 的判据是 `ASSERT-OK`（要素计数），**不比对像素** ⇒ 换光栅器不会挂回归；
  但 bmpdiff 的基准图要重建。
- 副作用（正面）：SDL 调用不再值钱后，第十刀"跳过退化路段"这类**为省调用而做的
  近似可以放宽**，画面能更准。

### 解锁的新优化（现在被 SDL API 挡着）

span 用 32 位字批量填充（替代逐像素 Bresenham）、按颜色分组消除状态切换、
多线程分块渲染（SDL renderer 不是线程安全的，自己的 fb 才能安全分片）、
粗线一次成型（现在是画 n 条偏移线）。

### ★ 踩的最大一个坑：退化段（两端坐标相同）**要画 1 个像素**

第一版按"零长线不产生像素"直接 return，z9 差 216 个像素。真相是 SDL 走
`HLINE(x,x,y)`，min==max 照样落一个点；只有点落在裁剪框外才什么都不画。
**别凭直觉改这条**（z9 有 67% 的段是退化的）。已在 `raster.h` 的注释里写死。

### 定位 216 像素的方法（可复用，三步）

1. **分层落盘**：面后/路后/线后各存一张 bmp ⇒ 面层 0、路层 216 ⇒ 锁定路网。
2. **同帧双画**：同一帧、同一批段，光栅写主画布、SDL 写另一张**起点内容相同**
   的画布 ⇒ 消掉"两次运行"的不确定性（这一步才是决定性的）。
3. **逐段隔离**：每段单独画进两张清空的小窗口（只清包围盒）⇒ 直接打印出不一致
   的段。汇总：**退化段 270,540、非退化段 0**。

★ 整帧只差 216 而隔离量差 27 万并不矛盾：退化点绝大多数随后被同等级邻段覆盖。
⇒ **小差异别当噪声，也别拿"差异小"推断"原因小"**。

### 窗口路径换了架构

离屏 surface 上画完（光栅画地图 + SDL 画文字/UI 混在同一张图）→ `UpdateTexture`
+ `RenderCopy` 贴窗，每帧 +2.6 ms，换来窗口和 map_shot **共用一套 paint_frame**。

## 第十四刀：面要素归因 + 三条被否决（已验收，细节 PLAN.md §30）

### 面要素 65 ms 归因（临时位开关）

遍历+预筛 3 / 每面固定开销 9 / **顶点投影 21** / 随机访存 6 / 填充 13 / 描边 10 /

规模：预筛后 113,933 个面（76,007 走打点、37,535 走完整管线、391 是复杂面），
顶点 114.6 万，扫描线只扫 267,624 行。

### 三条否决（都写进代码/PLAN 了，别再试）

1. **两遍合成一遍** — 慢 4 ms。随机访存那遍单独跑满才能把并发缺页拉满。
2. **合并"投影到同一像素"的相邻顶点** — 慢 2~4 ms。它像素精确、且 64% 顶点冗余，
   但"识别冗余"的成本高于"让冗余在下游被跳过"。
3. **路网加 geo 预筛省投影** — z9 投影后判越界的段是 **0 条**，瓦片索引已够准。

### 采纳：开 LTO

实测无额外收益。写进了 `CMakeLists.txt`（`check_ipo_supported` 兜底）。
`regress.sh --build` **22/22、零警告**。

## 内存布局（NMBIN）收益判别实验（午后）

- 问题：§31 归因说"面要素内存访问 17 ms > 投影 14 ms"，改 NMBIN 布局能换多少？
- 做法：临时开关 NAVIMAP_LAYOUT 在**真实帧**里旁路成三种布局（量完已删，树已复原，
  干净构建四档 0 像素差异）。
  - L0 现状：polyrefs 存 u32 节点下标 → 随机读 nodes.bin 28B 记录
  - L1 紧凑节点坐标表：8B/点，仍随机（+397 MB）
  - L2 内联环坐标：polyrefs 改存 {i32 lat,i32 lon} 8B/顶点，顺序读（+139 MB）
- 结果（同一时刻交替 3 轮，差值可信；L0 那列含开关开销 ~4 ms）：
  z9 L0 120 / L1 113 / **L2 104**；z11 58/56/51；z13 43/42/41；z15 31/31/30。
  ⇒ Δ(L0−L2) = **z9 −16 / z11 −7 / z13 −2 / z15 −1**；Δ(L0−L1) = −7/−2/−1/0。
  分阶段 z9：面 60→51（−9）、线 17→11（−6）、路 0、标注 0。
- 结论：**贵的是间接寻址不是 stride**（改 stride 只值 7 ms，去掉间接值 16 ms）；
  17 ms 内存开销里只捞得回 ~9 ms，剩下的 9.2 MB 顺序读不是零成本。
- 前提已核实：**polyrefs 只被渲染读，路由完全不碰** ⇒ 改它不影响路由。
- 代价：磁盘 +139 MB（3.8→3.94 GB，+3.7%）、NMBIN v3→v4、8 省重抽 57 秒；
  要丢"环顶点→节点下标"的关联（12B/条可保，但 +278 MB）。**待用户定夺**。
